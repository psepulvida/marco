The short version

  • The no em-dash rule names CHANGELOG.md, and the changelog has 104 em-dashes on 68 lines. All of them are in releases from 17 June to 5 August, before the rule. The pull request that added the rule (#905) left them there on purpose. Read literally, the rule asks for the edit that #905 reverted.
  • The file says a finished docs page "carries four sections". The template it points to says two of them can be left out. One page leaves one out. An agent obeying the root file would pad it, which the template forbids.
  • One open question: whether the ask-matt router should know about six user-invoked skills in in-progress/.
  • Everything mechanical holds: the manifest, the READMEs, the invocation flags, the links. The list is at the end.

The file

Commit d81f3a1 (29 September 2026), still the head of main when I published. AGENTS.md is a symlink to CLAUDE.md, so Claude Code and other agents read the same 3,850 bytes, 25 lines. It is not a style guide: it is a list of invariants about how the repository is laid out (which bucket a skill lives in, what must list it, what each page must contain), and almost every one of them can be checked by a script. I wrote one and ran it against the tree.

Finding 1: the rule includes the file it was written to leave alone

The last line of the file:

"No em-dashes anywhere in this repo's prose (SKILL.md files, docs, README.md, CHANGELOG.md, ADRs, changesets, code comments)."

On 1 October 2026, CHANGELOG.md has 104 em-dashes on 68 lines. git blame dates every one of those lines between 17 June and 5 August 2026, in releases committed by the release bot. The rule arrived on 19 August.

That is not an oversight. Pull request #905, "Remove all em-dashes from the repo", removed them from 99 files and then put the changelog back: "CHANGELOG.md is changeset-generated, so its historical entries are left alone (reverted to main's text) rather than hand-edited". Its test plan expects the search for the character to return matches only in CHANGELOG.md, "untouched on purpose". The same pull request added the line above.

What a fresh agent does: it has the rule and not the pull request. Asked to touch the changelog, or to check the repository against its own rules, it finds 68 violations of a rule that names the file, and the natural repair is the hand edit #905 decided against. The intent was clearly "do not add new ones"; the sentence says "anywhere".

A fix: say which part is meant. For example: "No em-dashes in new prose (...). Released entries in CHANGELOG.md are generated and stay as they are; changesets must not contain them."

Finding 2: four sections in one file, up to four in the other

The file: "A finished page carries four sections: What it does, When to reach for it, Common questions, and It's working if. writing-docs.md holds the template".

The template, .agents/writing-docs.md, on Common questions: "Omit the heading where there is nothing worth answering." On It's working if: "omit the heading where they stay vague." Its checklist adds that Common questions is "sized to what it found, not padded to match a richer skill's page".

The tree follows the template. 26 of the 27 docs pages for promoted skills have all four headings. docs/productivity/wait-what.md has no Common questions; it has two sections of its own instead.

What a fresh agent does: the root file loads in every session; the template is read only when the agent decides to open it. An agent that checks pages against the root file reports wait-what as unfinished and adds the missing section, which is the padding the template rules out.

A fix: "A finished page carries up to four sections (...); writing-docs.md says when two of them can be left out."

Both findings have the same shape: a short rule in the file every session loads, a longer and correct version somewhere the session may never look (a pull request, a linked template). A check for dead paths or contradictions inside the loaded files finds neither, because nothing is dead and the loaded text agrees with itself.

An open question: the router and in-progress skills

The file says ask-matt "is the router that maps every user-reachable skill", and that "a new skill it never mentions, or a stale one it still routes to, is a router that lies". It also defines a user-invoked skill as "reachable only by the human".

skills/in-progress/ has six skills, and all six are user-invoked: claude-handoff, loop-me, setup-ts-deep-modules, writing-beats, writing-fragments, writing-shape. scripts/link-skills.sh links them into the local skill folders ("in-progress/ IS still linked: it's public on purpose"). ask-matt mentions none of them. The plugin does not ship them, so for a plugin user the router is complete. For whoever runs the link script, it is not. I cannot tell which reader the rule means, and a fresh agent cannot either; one sentence in the file would settle it.

What holds

Checked by script against the tree at d81f3a1:

  • The 27 skills in engineering/ and productivity/ are exactly the 27 entries in .claude-plugin/plugin.json, and every entry exists. None of the 10 skills in misc/ or in-progress/ appears in the manifest or the top-level README.md.
  • Every promoted skill is linked to its SKILL.md from the top-level README.md. Every bucket README.md links every skill in its bucket, and the promoted ones and the top-level one group them into User-invoked and Model-invoked.
  • All 22 skills with disable-model-invocation: true also set allow_implicit_invocation: false in their agents/openai.yaml, and no skill has one flag without the other.
  • Every promoted skill has its page under docs/; the one page left for a removed skill, resolving-merge-conflicts, is marked archived, as the file says it should be.
  • Every file the root file links exists. Outside the changelog, there is not one em-dash in the repository.

For a file made almost entirely of checkable claims, that is a very good result. It is also why the two findings are worth a page: when everything else in a file is true, an agent has no reason to doubt the two lines that are not.

What I did not check

I did not run claude plugin validate, the link script or any skill. I did not read the skills themselves, only what the root file says about them. The counts are from a clone of d81f3a1 and the GitHub API on 1 October 2026, and will drift; the repository has fourteen changesets waiting for the next release.
